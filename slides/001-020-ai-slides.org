  and Python about 2.34 million, a difference of roughly 6%. Median usage is

- Cached context is substantial: about 37.7 million tokens for Scala and
  18.2 million for Python. Excluding it makes this chart easier to read, but
  leaves out a large share of recorded consumption.
- Python's Day03 part2 spike is about 487,000 tokens, mostly fresh input.
  The report attributes it to verification output from brute-force checks
  against samples and 2,000 random banks flooding the context.
- Scala's Day09 part2 spike is about 543,000 tokens, including 59,000 output
  tokens. The report links it to geometry design, extensive cross-checking,
  and an overlapping solver session that appears to have inflated context.
- Scala's next-largest bar is Day05 part2 at about 268,000 tokens.
  Its interval-merging solution also involved build-cache recovery and repeated
  verification, so token usage includes development overhead.
- These are selected solver-run counts, excluding gather, submit, review,
  and superseded attempts such as Python's first Day01 part1 run. They measure
  one stage of the workflow rather than the entire factory's consumption.
- Token counts alone do not establish a money ranking: fresh input, cached
  input, and output have different prices. The modest aggregate gap here
  supports a narrower claim about this token metric, not equal dollar costs.
- Note: Highlight that  the two outliers are  more a bug in the  harness, than a
  reflection on the language to solve the problem.

#+BEGIN_NOTES
- Each bar rates the generated code for one puzzle part from 1, poor, to 5,

- The score averages five equally weighted dimensions: correctness robustness,
  readability, idiomatic language use, test depth, and simplicity/efficiency.
  It assesses code and tests beyond whether the puzzle answer was accepted.
- Python averages 4.67 and Scala 4.04, with Python ahead on 16 parts and two
  ties. Both languages solve all 18 parts, while this rubric favors the Python
  implementations overall.
- The largest gaps are 1.4 points on Day03 part1, Day04 part2, and Day05 part1.
  The report credits Python's linear digit scan, queue-based grid updates,
  and merged-range lookup over Scala's more repetitive scans.
- Test depth also contributes: the report describes broader sample, real-input,
  and boundary tests in Python. On Day07, it additionally favors Python's
  structure and input validation despite similar algorithmic complexity.
- Day08 ties at 4.0 for both parts, with comparable union-find approaches
  and duplicated helpers. Day01 is also close, at 5.0 for Python and 4.8 for
  Scala on both parts.
- Muse Spark produced these ratings in a single judging pass using source
  code and automated evidence. There was no blinded panel or second model,
  and efficiency was assessed by code reading rather than runtime benchmarks.
- The chart shows a quality advantage for Python under this rubric, alongside
  broadly good Scala results. It does not establish statistical significance
  or a general limit on the quality AI can produce in Scala.

* Part 2 - The results

- Codex showed no statistically significant performance/quality difference between Scala and Python
- Language popularity alone does not explain code-generation performance
- The myth does not hold as a blanket rule

#+BEGIN_NOTES
- State the paper's overall finding that Codex performed comparably on Scala
  and Python in this benchmark. That concerns functional correctness, rather
  than maintainability.
- Popularity correlated with performance, but did not determine it. Some less
  common languages performed well.
- Return to the blanket hypothesis: language frequency alone is insufficient to
  predict generated-code success. Keep that conclusion tied to the tested
  models and tasks.
#+END_NOTES

* My experience/opinion

- The size of the corpus matters less than expected
- The quality of the corpus matters (less good/young code is better than a lot of bad/old code)
- The language being statically typed (with a good compiler and good error messages) matters
  - Getting it right the first time matters less, than being able to iterate towards good code

#+BEGIN_NOTES
- Mark this transition explicitly as my interpretation of the evidence. I
  suspect useful examples and feedback can matter more than raw corpus size
  alone suggests.
- Explain why I value a compiler in an agent loop: it supplies concrete errors
  that can guide the next edit. Treat that as a proposed mechanism rather than
  something this experiment isolated.
- Focus on the ability to converge on a good result through tests and
  corrections. Invite the audience to compare that with their own Scala
  development experience.
#+END_NOTES
